# NCRPTS-Reference — VERSION DELTAS

> **What this file is.** A map of the six sample-project snapshots in this repo (`base`, `V1`, `V2`, `V3-A`, `V3-B`, `V4`), what changes between them, and how the loose `.sql` / `.mwb` database files line up. Generated by diffing the folders, not from memory. Keep it in `index/`; drop a copy into the project knowledge so any chat can jump straight to the right version.
>
> **The one thing to understand first:** the sample project is a **retail / inventory teaching codebase** wearing an **"Earth University" college costume**. The college menus (attendance, batchregistration, class, student…) are almost all empty placeholder folders. The parts that are *actually built* are the **admin/RBAC core** plus a growing chain of **inventory modules** (items → suppliers → purchase orders). Ignore the college domain; harvest the machinery. This is the same "vehicle vs destination" rule from `PROJECT-CONTEXT.md`.

|---|---|---|---|---|
| **base** | 58 | 63 / 19 | `HarvestSuperApplication` | The raw seed. Same feature set as V1, but still carries `HarvestSuper` naming + a few `harvest.png`/supermarket leftovers and an **older, smaller DB model**. This is your intended starting point ("first facilitating modules"). |
| **V1** | 58 | 63 / 19 | `EarthuniversityApplication` | Same features as base, **renamed** main class + assets to "Earthuniversity", slightly cleaned. Effectively "base, tidied". |
| **V2** | 77 | 75 / 20 | `Earthuniversity…` | **+ Item master data:** entities Brand, Category, Subcategory, Categorybrand, Item, Itemstatus, Unittype (+ their controllers). Client gains the `item` module. |

**Reading the two "V3" folders:** they are not rivals — they're two halves of one step. **V3-A = supplier back-end**, **V3-B = supplier front-end on top of it**. If you want the complete supplier slice, take **V3-B**. V3-A is only interesting if you specifically want to see the server-first state.

## 3. The V3-A → V3-B controller reshuffle (minor, but noted so it doesn't confuse you)

- V3-B (and V4) **drop `UserAuthorityController`** that existed in base…V3-A; its behaviour is folded into `UserController` + the security package. If you diff user-management code across the V3 line, that's why a file "disappears".
- V3-B **adds** `SupplierController`, `SupplierstatusController`, `SuppliertypeController` (the client-facing supplier endpoints).

Nothing else structural changes across the whole chain — same `controller / dao / entity / report / security / util` packages throughout.

## 4. Database files — how the loose `.sql` / `.mwb` map to versions

The DB track is numbered **independently** of the code (as you said). The files use a cumulative naming convention: **`harvestsuper-v1-vN`** = "the MySQL Workbench model as it had grown by DB-version N". Content-hashing them collapses the pile into just a few distinct states:

| DB state | Distinct file (by content) | Size | Present in folders | Notes |
|---|---|---|---|---|
| **v1–v4** (schema + seed) | `harvestsuper-v1-v4.sql` | 773 KB | V2, V3-A, and **byte-identical** to `base/harvestsuper-base.sql` | The schema was **stable from v1 through v4** — that's why one file spans them. This is your baseline DB. |
| **v5** | `harvestsuper-v1-v5.sql` | 4.2 MB | V3-A, V3-B | Big jump — bulk **seed/demo data** loaded (schema barely changes; the size is data). |
| **v6** | `harvestsuper-v1-v6.sql` | 4.26 MB | V4 | Minor delta over v5 (purchase-order tables). |
| **v7** | *(model only — no `.sql` dump)* | — | V4 (`harvestsuper-v1-v7.mwb`) | Latest **model** exists but was never dumped to SQL. If you need a v7 DB, forward-engineer it from the mwb. |

**Model (`.mwb`) nuance:** `base/harvestsuper-base.mwb` is **unique and smaller** (20 KB) than the v1-v4 model (28 KB) even though their SQL dumps are identical — base's model file is an earlier save. Also V3-B's live `.mwb` equals V3-A's `.mwb.bak` (just a later save-state of the same model). None of this matters for building; the **`.sql` dumps are your source of truth**, the `.mwb`/`.mwb.bak` are Workbench working files.

**Practical rule:** to stand up any version's database, restore the **largest-numbered `.sql` in or below that version's folder**. For `base`/`V1` → the 773 KB dump; for the V2/V3 line → `v5`; for V4 → `v6`.

## 5. Stack (identical across all versions — confirmed from the files)

- **Server:** Spring Boot 2.7.10 · **Java 8** (`JavaVersion.VERSION_1_8` in `build.gradle.kts` — note: *8*, not 11) · Gradle Kotlin DSL · packaged WAR · Spring Data JPA + Hibernate · JWT + Spring Security · port 8080.
- **Client:** Angular 15.1 · Angular Material 15 + ng-bootstrap · Google Charts · single root `AppModule` (no lazy modules) · port 4200.
- **DB:** MySQL, schema `sltdb`, **no `ddl-auto`** (schema must pre-exist — restore the dump).
- **Group / package:** `lk.earth` / `lk.earth.earthuniversity`; npm package `earth-uni`. → all of this is what you rename to your project (see `CLAUDE.md` and `PROJECT-CONTEXT.md` §12).

## 6. TL;DR — which folder do I open?

- **Starting my project?** → **`base`** (rename it, then iterate). It's the minimal RBAC seed.
- **Want the cleanest reference for the RBAC/auth pattern?** → **V1** (same as base, tidier naming).
- **Copying the Item/master-data pattern?** → **V2**.
- **Copying the Supplier slice full-stack?** → **V3-B** (not V3-A).
- **Copying purchase-orders, or want the most complete example of anything?** → **V4**.
- **Need a database?** → restore the right `.sql` per §4.
